Domínios locais

Acesse containers por nome em *.localhost, descubra a porta certa automaticamente e habilite HTTPS com a CA interna do PodStack.

PodStack 0.1.3Documentação de usuário

Visão geral

O PodStack tem um proxy HTTP em loopback na network.httpPort (18080 por padrão). Ele resolve o Host para um container e encaminha para uma porta TCP publicada. Para o navegador, http://web.localhost:18080/ chega ao container web sem editar /etc/hosts e sem root.

O HTTPS é opcional e usa Caddy com uma CA interna na network.httpsPort (18443 por padrão). O certificado é emitido sob demanda para *.localhost e *.podstack.local.

Domínios *.localhost na prática

  1. Publique uma porta TCP na criação do container, por exemplo 8080:80.
  2. Abra http://localhost:18080/ para ver o índice de containers que publicam porta.
  3. Abra http://<nome>.localhost:18080/ para acessar o container pelo nome.
  4. Se houver várias portas publicadas, o proxy detecta a que responde HTTP; se nenhuma responder, usa a primeira publicada.
  5. Para forçar uma porta, adicione a label dev.podstack.http-port ao container.
# exemplo de criação pela GUI: web com 8080:80
curl -I http://web.localhost:18080/
curl -I http://localhost:18080/

getent hosts web.localhost
podstack config get network.httpPort

A URL usa a porta do proxy, não a porta interna do container. O proxy fecha a conexão após a resposta e adiciona X-Forwarded-For, X-Forwarded-Proto e X-Forwarded-Host. network.bridge=false desliga o proxy HTTP e o DNS.

Página de índice

http://localhost:<network.httpPort>/ serve uma página com os containers que publicam porta TCP: nome, estado, porta publicada e a URL http://<nome>.localhost:<porta>/. Apenas GET e HEAD são aceitos; os demais métodos recebem 405. Um nome inexistente retorna 404 com a lista de serviços.

Detecção automática da porta

Na primeira requisição, o proxy testa as portas TCP publicadas em paralelo, com timeout de 300 ms e HEAD /. A resposta que começa com HTTP/ vence. As portas comuns (80, 8080, 3000, 5000, 8000, 8081, 8888, 443 e 8443) são preferidas; depois as demais em ordem crescente. Com uma única porta publicada, ela é usada direto, sem probe.

O resultado é cacheado por container (ID), digest da imagem e portas publicadas. Recriar o container troca o ID e invalida o cache; o limite é de 64 entradas e 10 minutos. Labels dev.podstack.http-port e dev.podstack.https-port sobrescrevem a detecção; a label dev.podstack.domains adiciona domínios customizados ao roteamento por Host e ao índice.

Domínios *.podstack.local e DNS

*.localhost resolve para loopback pelo próprio sistema. Já *.podstack.local usa o DNS userspace do PodStack em 127.0.0.1:5353 e um drop-in do systemd-resolved. Em 0.1.3, a instalação do drop-in ainda não está ligada à GUI/CLI; sem ele, o nome não resolve.

Para usar *.podstack.local, instale o drop-in manualmente (operação de sistema; revise antes):

sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/podstack.conf >/dev/null <<'EOF'
[Resolve]
DNS=127.0.0.1:5353
Domains=~podstack.local
EOF
sudo systemctl reload systemd-resolved

# testar
resolvectl query web.podstack.local
getent hosts web.podstack.local

O DNS escuta UDP e, quando disponível, TCP. Ele usa SO_REUSEADDR para conviver com Avahi/mDNS em 0.0.0.0:5353; se ainda assim não responder, o journal mostra o aviso. O DNS só sobe com network.bridge=true. Para a maioria dos casos, prefira *.localhost, que não exige root, DNS ou CA.

O drop-in é manual nesta versão

O helper tem a API de DNS, mas a fiação automática ainda não foi ligada à GUI/CLI. Os passos acima são os mesmos do guia de troubleshooting. Para remover, apague /etc/systemd/resolved.conf.d/podstack.conf e recarregue o resolved.

HTTPS com CA interna

  1. Instale o Caddy, se ainda não estiver presente: podstack setup --apply components --caddy.
  2. Habilite o HTTPS: podstack config set network.https true.
  3. Reinicie o daemon: systemctl --user restart podstack.service.
  4. Acesse https://<nome>.localhost:18443/.
  5. Teste sem alterar o trust store com curl --cacert <root.crt>.
podstack setup --apply components --caddy
podstack config set network.https true
systemctl --user restart podstack.service

curl --cacert ~/.local/share/podstack/caddy/storage/pki/authorities/local/root.crt \
  https://web.localhost:18443/

A CA local fica em ~/.local/share/podstack/caddy/storage/pki/authorities/local/root.crt. O navegador não confia nela por padrão. A importação é manual nesta versão; no Fedora, copie o arquivo para /etc/pki/ca-trust/source/anchors/podstack-local-ca.crt e rode sudo update-ca-trust. No Debian/Ubuntu, use /usr/local/share/ca-certificates/ e sudo update-ca-certificates. No Firefox, importe o root.crt nas autoridades do próprio navegador.

Containers criados ou duplicados pelo PodStack recebem a CA montada read-only quando o arquivo existe. A label dev.podstack.ca=false faz opt-out. Containers de Compose ficam pendentes: o provider externo monta os volumes.

Confiar na CA afeta o sistema

Adicionar a CA ao trust store do sistema faz todas as aplicações confiarem nela. Use apenas em desenvolvimento e remova o arquivo quando não precisar mais. O helper tem a ação TrustCa, mas a fiação automática não está pronta em 0.1.3.

Labels dev.podstack.*

Label Efeito Onde usar
dev.podstack.http-port Força a porta publicada usada pelo HTTP. Aceita a porta do container ou do host. Container; útil quando há várias portas publicadas.
dev.podstack.https-port Força a porta publicada usada pelo HTTPS; o proxy conecta com TLS sem verificação de peer. Container com backend HTTPS.
dev.podstack.domains Adiciona domínios customizados ao roteamento por Host e ao índice. Container; separe os domínios conforme o formato aceito pela label.
dev.podstack.ca=false Não monta a CA local no container. Container que não deve receber a CA.

Labels inválidas caem na detecção normal, sem quebrar o proxy. Para aplicar uma label, recrie o container (a label é lida na criação) ou use o Compose, lembrando que o roteamento de domínios customizados via Compose ainda está pendente.

Expor na LAN

Para acessar os domínios de outros dispositivos, ative network.exposeLan=true e reinicie o daemon. O proxy HTTP passa a escutar em 0.0.0.0/:: e o Caddyfile usa bind 0.0.0.0 no HTTPS. O firewall do host precisa ser liberado separadamente; o PodStack não abre as portas do proxy automaticamente.

podstack config set network.exposeLan true
systemctl --user restart podstack.service

# firewalld (regra runtime; um reload/restart a remove)
sudo firewall-cmd --add-port=18080/tcp
sudo firewall-cmd --add-port=18443/tcp

# ufw
sudo ufw allow 18080/tcp
sudo ufw allow 18443/tcp

Na CLI

O proxy e o HTTPS são configurados pelas chaves network.*. O CLI não cria o container por você, mas permite conferir portas publicadas, alterar as portas do proxy e testar o resultado com curl.

Comando O que faz
podstack config get network.httpPort Mostra a porta do proxy HTTP.
podstack config get network.httpsPort Mostra a porta do proxy HTTPS.
podstack config set network.https true Habilita o HTTPS; exige reinício.
podstack config set network.exposeLan true Expõe o proxy na LAN; exige reinício.
podstack ps Mostra as portas publicadas dos containers.
podstack status Confirma daemon e engine antes de testar. 
podstack config get network.httpPort
podstack config get network.httpsPort
podstack ps
curl -I http://web.localhost:18080/

podstack config set network.https true
podstack config set network.exposeLan true
systemctl --user restart podstack.service

Limitações

  • Portas não publicadas não podem ser encaminhadas no rootless (T6-10). Publique a porta na criação do container ou no Compose.
  • As portas 80/443 não são ativadas automaticamente pela GUI/CLI em 0.1.3; use 18080/18443. O helper tem BindPorts, mas a fiação do app ainda não a chama.
  • CA e *.podstack.local são manuais: a confiança na CA e o drop-in do resolved não têm fluxo pronto na GUI/CLI.
  • Domínios customizados via Compose (T6-08) estão pendentes; a montagem da CA em containers de Compose também.
  • Não há k8s.podstack.local em 0.1.3.
  • O proxy usa a primeira porta publicada quando nenhuma responde HTTP; se o serviço não for HTTP, a URL pode não funcionar como esperado.
