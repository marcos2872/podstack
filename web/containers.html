Containers

Crie, opere e inspecione containers Podman sem sair da GUI — com logs, terminal, arquivos, estatísticas, health e inspect no mesmo detalhe.

PodStack 0.1.1Documentação de usuário

Visão geral

A seção Containers é a tela principal do PodStack. Ela combina uma lista com filtros, um inspetor lateral e um detalhe expansível com nove abas. Os containers criados fora do PodStack também aparecem, desde que o daemon consiga reconciliar o estado com o Podman.

As ações usam a API Libpod do podman.socket. O estado é reconciliado por eventos: a linha pode mostrar starting ou uma transição otimista antes de o engine confirmar. Health aparece como healthy, unhealthy, starting ou sem healthcheck.

Na interface

Listar, filtrar e selecionar

  1. Abra Containers na barra lateral.
  2. Use as abas Todos, Em execução e Parados para filtrar por estado.
  3. Digite na busca da seção (atalho Ctrl+F) para filtrar por nome, imagem ou porta.
  4. Selecione uma linha para abrir o inspetor. Use Ctrl+clique ou Shift+clique para multi-seleção.
  5. Com vários itens selecionados, use as ações em lote da barra; Start all e Stop all afetam todos os containers conhecidos.

As setas do teclado navegam pela lista; Enter abre o detalhe; Esc desseleciona. F5 atualiza e Ctrl+Enter inicia ou para o container selecionado.

Criar um container

  1. Clique em Novo container (ou Ctrl+N).
  2. Preencha Imagem (por exemplo, nginx:alpine). Se a imagem não existir localmente, faça o pull antes em Imagens.
  3. Defina Nome, Comando, Portas, Env, Volumes, Workdir e Usuário conforme a necessidade.
  4. Marque as opções: Remover ao parar, Init, Privileged e Expor portas na LAN.
  5. Clique em Criar e iniciar.

O campo Portas aceita o formato 8080:80 ou 127.0.0.1:8081:81. O campo Env aceita A=B, C=D; Volumes aceita /host:/container, /tmp:/mnt. Sem Expor portas na LAN, as portas publicadas ficam em 127.0.0.1.

A imagem precisa existir

A criação usa a imagem local. O Podman retorna erro se ela não estiver disponível; baixe com Pull ou podstack images pull <imagem>.

Ciclo de vida e ações do inspetor

Com um container selecionado, o inspetor mostra o nome, a imagem, o estado e as ações principais:

  • Iniciar, Parar, Reiniciar e Remover no cabeçalho.
  • Pausar e Despausar no bloco Ações.
  • Matar envia o sinal de término pelo engine; use com cuidado.
  • Abrir porta abre http://localhost:<porta> para a primeira porta publicada.
  • Renomear abre um diálogo com o novo nome; Duplicar cria uma cópia a partir do container selecionado.
  • Expandir abre o detalhe completo em overlay. O x ou Esc fecha e encerra os streams e a sessão de terminal.

O botão de lixeira remove o container após confirmação. A GUI usa remoção forçada e preserva os volumes; não há caixa “remover volumes” nesta versão.

Remoção é permanente

O container é removido permanentemente. Se precisar dos dados de um volume nomeado, eles continuam no volume; binds do host não são afetados. A API RPC containers.remove aceita volumes, mas a GUI/CLI 0.1.1 não expõe esse controle.

Detalhe: nove abas

O detalhe expandido (ContainerDetail) abre com Visão geral e oferece:

Aba O que mostra Ações
Visão geral Cards de CPU, RAM, rede ↓/↑ e disco R/W com sparklines de 60 amostras; stats a cada ~1 s. Pausar/retomar a atualização quando disponível.
Logs Stream ao vivo de stdout/stderr no detalhe. Seguir, busca, Wrap, Timestamp, Copiar e Limpar.
Info Estado, PID/exit code, health, criado/iniciado, restart policy, imagem/digest, entrypoint/comando, workdir, usuário, portas e labels. —
Ambiente Todas as variáveis Config.Env; chaves com token, password, secret, authorization ou key ficam mascaradas. Mostrar valores e Copiar (respeita o mascaramento).
Redes Redes conectadas com IP, gateway, MAC, aliases e network ID; portas publicadas. —
Volumes Mounts com tipo, nome, origem, destino, driver, RW e propagação. —
Arquivos Navegação no filesystem do container. Clicar em um arquivo baixa para ~/Downloads; Enviar faz upload do caminho local informado.
Terminal Sessão embutida podman exec -it <id> /bin/sh. Nova sessão em janela abre um terminal externo.
Inspect JSON completo do Libpod (containers.inspect), indentado. Copiar.

Os atalhos Ctrl+Shift+L e Ctrl+Shift+T abrem logs e terminal do container selecionado. O terminal embutido também pode ser aberto em uma janela separada; o fechamento da janela encerra a sessão.

Rootful opt-in

O padrão é rootless. Para usar o socket rootful, abra Configurações (item Settings na barra lateral), escolha a categoria Engine e altere engine.mode para rootful. A mudança exige reiniciar o PodStack e o seu usuário precisa de acesso ao socket correspondente (normalmente /run/podman/podman.sock).

Rootful é opt-in explícito. A GUI mostra o modo no rodapé e os erros de permissão explicam a limitação. O PodStack não usa setuid nem sudo para containers.

Na CLI

O CLI 0.1.1 lista e opera containers existentes, mas não cria, inicia, para nem remove containers. Para essas ações, use a GUI. As operações disponíveis são:

Comando Flags O que faz
podstack ps --all/-a, --running/-r, --stopped/-s, --format table|json, --quiet/-q Lista containers. Sem filtro, mostra apenas os que estão em execução; --all inclui parados.
podstack inspect <id|nome> — Imprime o JSON bruto do container.
podstack exec <id|nome> -- <cmd...> — Execução one-shot; imprime stdout e devolve o exit code do comando. Para shell interativo, use a aba Terminal da GUI.
podstack pause <id|nome> — Pausa o container.
podstack unpause <id|nome> — Despausa o container.
podstack kill <id|nome> --signal S Envia um sinal, por exemplo SIGTERM.
podstack checkpoint <id|nome> --leave-running, --tcp-established, --json Cria um checkpoint CRIU; depende do host.
podstack restore <id|nome> --tcp-established, --json Restaura o checkpoint CRIU do container. 
podstack ps --all
podstack ps --format json | jq -r '.items[].name'
podstack inspect web
podstack exec web -- sh -c 'echo olá'
podstack pause web
podstack unpause web
podstack kill web --signal SIGTERM
podstack checkpoint web --leave-running
podstack restore web

Checkpoint/restore depende do host

CRIU exige cgroup v2 com delegação e o binário criu disponível. Em rootless, muitos hosts não permitem o checkpoint. Se o host não oferecer suporte, use rootful (opt-in) ou trate o recurso como indisponível. Detalhes em CRIU e cgroup rootless.

Limitações

  • O CLI não cria, inicia, para nem remove containers; o ciclo de vida completo está na GUI.
  • A remoção pela GUI usa force e preserva volumes. A API aceita volumes, mas não há controle na GUI/CLI 0.1.1.
  • O diálogo de criação não expõe CPU/memória nem restart policy; esses campos podem existir no contrato RPC, mas não na interface.
  • Checkpoint/restore CRIU é dependente do host e costuma falhar em rootless.
  • Portas não publicadas não podem ser adicionadas depois do create no modo rootless. Publique na criação ou use Compose.
  • Logs e terminal não têm comando equivalente no CLI 0.1.1; use a GUI ou o Podman diretamente.
