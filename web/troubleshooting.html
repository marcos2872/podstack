Solução de problemas

Comece pelos diagnósticos que não alteram nada, confira socket, Podman, helper e KVM e gere um relatório redigido quando precisar de ajuda.

PodStack 0.1.4Documentação de usuário

Primeiros checks

podstack status
podstack doctor
systemctl --user status podstack.socket podstack.service
systemctl --user status podman.socket
journalctl --user -u podstack.service -n 200 --no-pager

# relatório redigido para suporte
podstack report --include-logs

O report fica em ~/.local/state/podstack/reports/ com permissão 0600; o comando imprime o caminho e o SHA-256. Revise o conteúdo antes de compartilhar: ele é redigido, mas pode conter nomes de containers, caminhos e configuração.

Daemon e socket

Sintomas: Tempo esgotado aguardando o podstackd., PODSTACK_DAEMON_UNAVAILABLE, ou podstack status com exit 7.

systemctl --user status podstack.socket
systemctl --user status podstack.service
systemctl --user daemon-reload
systemctl --user start podstack.socket
ls -l "$XDG_RUNTIME_DIR/podstack/control.sock"
stat -c '%a %U %G' "$XDG_RUNTIME_DIR/podstack/control.sock"
journalctl --user -u podstack.service -n 200 --no-pager

O socket deve ser um Unix socket 0600, no diretório 0700, pertencente ao seu usuário. O daemon é ativado na primeira conexão. Causas comuns: units não recarregadas após atualização, socket inativo, daemon que falhou no start, PODSTACK_CONTROL_SOCKET apontando para outro caminho ou permissão errada. Não use chmod 0666.

Em desenvolvimento, inicie o daemon manualmente para diagnóstico:

./build/dev/podstackd --socket /tmp/podstack-dev.sock
PODSTACK_CONTROL_SOCKET=/tmp/podstack-dev.sock ./build/dev/podstack status

Podman e engine

Sintomas: PODSTACK_ENGINE_UNAVAILABLE, engine: unavailable, podman: unavailable ou listas vazias mesmo com containers existentes.

systemctl --user status podman.socket
systemctl --user enable --now podman.socket
podman --version
podman info
ls -l "$XDG_RUNTIME_DIR/podman/podman.sock"
podstack setup --apply socket
podstack status

O PodStack usa o Podman rootless por padrão e espera o socket em $XDG_RUNTIME_DIR/podman/podman.sock. Se você usa outro caminho, ajuste PODSTACK_PODMAN_SOCKET ou engine.socketPath. No Fedora, o PodStack 0.1.3 espera Podman 5.8+; no Ubuntu 24.04+, Podman 4.9+ (5.8 recomendado).

No modo rootful (engine.mode=rootful), o socket é /run/podman/podman.sock e seu usuário precisa de acesso ao grupo correspondente. Rootful é opt-in explícito; a GUI mostra o badge e o aviso.

Helper e polkit

Sintomas: PODSTACK_HELPER_REQUIRED, PODSTACK_HELPER_UNAVAILABLE, setup que não instala pacotes e prompt de polkit que não aparece.

systemctl status podstack-helper.service
journalctl -u podstack-helper.service -n 100 --no-pager
pkaction --action-id dev.podstack.helper.install-packages --verbose

# O helper faz parte do pacote principal desde a 0.1.1.
sudo systemctl enable --now podstack-helper.service

O helper usa D-Bus de sistema e polkit. Ele precisa de uma sessão ativa com agente de autenticação (GNOME/KDE/niri com polkit agent). Em SSH sem sessão gráfica, a autorização pode falhar; rode o setup no desktop. O helper não aceita Exec/shell: ações fora da allowlist são recusadas por design. Se você não precisa de ações privilegiadas, o podman.socket pode ser ativado manualmente ou por podstack setup --apply socket; containers e machines não dependem do helper para operar.

KVM, QEMU e virtiofsd

Sintomas: criação de machine falha ou fica em error, machine muito lenta, erro de virtiofsd nos mounts.

ls -l /dev/kvm
test -r /dev/kvm && test -w /dev/kvm && echo "KVM ok"
groups
qemu-system-x86_64 --version
virtiofsd --version
podstack setup --check

# liberar KVM para o seu usuário (depois saia e entre na sessão)
sudo usermod -aG kvm "$USER"

Sem /dev/kvm, o PodStack usa TCG (-accel tcg), que funciona mas é muito mais lento. A virtualização precisa estar habilitada na BIOS/UEFI; em VM aninhada, o hipervisor precisa expor VT-x/AMD-V.

Se o virtiofsd estiver fora do path padrão, defina PODSTACK_VIRTIOFSD_BINARY ou instale em /usr/libexec/virtiofsd (fallback). O setup verifica QEMU, OVMF e virtiofsd; se um obrigatório estiver ausente, a tela principal fica bloqueada. Para uma machine que não sobe:

podstack machine info dev
podstack machine logs dev --tail 200
podstack machine console dev --no-follow --tail 65536
journalctl --user -u podstack.service -n 200 --no-pager

OVMF no Ubuntu

Na 0.1.2, o check só reconhecia os caminhos do Fedora (/usr/share/edk2/ovmf/OVMF_CODE.fd). O pacote ovmf do Ubuntu instala /usr/share/OVMF/OVMF_CODE_4M.fd e OVMF_VARS_4M.fd, então a instalação manual não destravava a etapa. A 0.1.3 reconhece esses arquivos e o setup instala ovmf, qemu-system-x86, qemu-utils e virtiofsd via apt.

Se você ainda está na 0.1.2, instale o pacote e crie os links esperados pelo app:

sudo apt install -y ovmf qemu-system-x86 qemu-utils virtiofsd
sudo mkdir -p /usr/share/edk2/ovmf
sudo ln -sf /usr/share/OVMF/OVMF_CODE_4M.fd /usr/share/edk2/ovmf/OVMF_CODE.fd
sudo ln -sf /usr/share/OVMF/OVMF_VARS_4M.fd /usr/share/edk2/ovmf/OVMF_VARS.fd

Quando o helper falha ao instalar, o setup mostra a mensagem no painel de log e no rodapé; journalctl -u podstack-helper.service -n 100 --no-pager traz o erro do apt/dnf.

O console é texto do serial; não há VNC. Se o cloud-init falhar, o estado fica error e o log mostra o estágio. O virtiofsd rootless usa --sandbox=namespace; o modo chroot exige root.

Machines, SSH e known_hosts

Sintomas: podstack ssh dev não conecta, ssh dev.podstack não existe ou usa a chave errada, machine pull/push falham.

podstack machine list
podstack machine info dev
podstack machine port ls dev
podstack ssh dev -- uname -a

# se a machine foi recriada e a chave de host mudou
ssh-keygen -R "[127.0.0.1]:32222"

A machine precisa estar running. O usuário padrão é podstack; a porta SSH é publicada em 127.0.0.1 e aparece em machine info/machine list. O PodStack gera a chave ed25519 e grava o bloco gerenciado em ~/.ssh/config quando ssh.manageConfig=true. Se você desativou essa opção, o alias <nome>.podstack não existe; use podstack ssh dev.

O agent forwarding é desligado por padrão. Com --forward-ssh-agent/ForwardAgent yes, processos no guest podem usar as chaves do seu agent; ative só em machines confiáveis. A porta SSH administrativa é publicada em 127.0.0.1; a chave ssh.exposePort existe no schema, mas está oculta e sem efeito no app 0.1.3.

X11

Use podstack ssh dev --x11 (adiciona -X) ou --x11-trusted (adiciona -Y). O host precisa de DISPLAY e XAUTHORITY; o guest precisa de xauth e de um cliente X11. Wayland nativo não é encaminhado pelo SSH — o encaminhamento é X11.

echo "$DISPLAY"
podstack ssh dev --x11 -- xeyes
podstack ssh dev --x11-trusted -- xterm

VMs novas recebem xauth e x11-apps (Debian/Ubuntu) ou xorg-x11-apps (Fedora) via cloud-init, além do drop-in /etc/ssh/sshd_config.d/10-podstack-x11.conf. VMs antigas precisam do passo manual.

Portas, proxy e firewall

Sintomas: http://nome.localhost:18080/ retorna 404, a porta 18080/18443 está em uso, ou o serviço funciona no host mas não na LAN.

ss -ltnp | grep -E ':18080|:18443'
curl -v http://web.localhost:18080/
curl -I http://localhost:18080/
podstack config get network.httpPort
podstack config get network.httpsPort
podstack ps

O proxy HTTP escuta em loopback na network.httpPort (18080). O HTTPS, quando habilitado, escuta na network.httpsPort (18443). A URL usa a porta do proxy, não a porta interna do container.

  • 404: o container não tem porta TCP publicada ou o nome não corresponde a um container. Publique a porta na criação; o Podman rootless não publica portas depois do create (T6-10).
  • Porta em uso: escolha outra porta com podstack config set network.httpPort 19080 e reinicie systemctl --user restart podstack.service.
  • LAN: podstack config set network.exposeLan true e reinicie. O firewall do host precisa ser liberado separadamente.
# firewalld (regra runtime; um reload/restart a remove)
sudo firewall-cmd --add-port=18080/tcp
sudo firewall-cmd --add-port=18443/tcp

# ufw
sudo ufw allow 18080/tcp
sudo ufw allow 18443/tcp

Portas 80/443

O helper tem a API de BindPorts, mas a GUI/CLI 0.1.3 não a aciona. Use 18080/18443. Se network.bridge=false, o proxy HTTP e o DNS ficam desligados.

HTTPS e CA

Sintomas: https://nome.localhost:18443/ não abre, o navegador mostra certificado inválido ou o daemon registra que o HTTPS está indisponível.

caddy version
podstack config get network.https
podstack config get network.httpsPort
journalctl --user -u podstack.service -n 100 --no-pager

podstack setup --apply components --caddy
podstack config set network.https true
systemctl --user restart podstack.service

A CA local fica em ~/.local/share/podstack/caddy/storage/pki/authorities/local/root.crt. Teste sem alterar o trust store:

curl --cacert ~/.local/share/podstack/caddy/storage/pki/authorities/local/root.crt \
  https://web.localhost:18443/

O navegador não confia na CA por padrão. A importação é manual nesta versão. No Fedora:

sudo cp ~/.local/share/podstack/caddy/storage/pki/authorities/local/root.crt \
  /etc/pki/ca-trust/source/anchors/podstack-local-ca.crt
sudo update-ca-trust

# remover a confiança
sudo rm -f /etc/pki/ca-trust/source/anchors/podstack-local-ca.crt
sudo update-ca-trust

No Debian/Ubuntu, copie para /usr/local/share/ca-certificates/podstack-local-ca.crt e rode sudo update-ca-certificates. Em Firefox, importe o root.crt nas autoridades do próprio navegador. Se o TLS funcionar mas a resposta for 502, o problema está no backend: confirme que o container publica a porta e que http://web.localhost:18080/ responde. Se o certificado não corresponder ao nome, use um domínio coberto por *.localhost/*.podstack.local ou ajuste a label de porta/domínio.

DNS e *.podstack.local

*.localhost não precisa de configuração. Teste com getent hosts web.localhost. *.podstack.local usa o DNS userspace em 127.0.0.1:5353 e um drop-in do systemd-resolved. Em 0.1.3, a instalação desse drop-in ainda não está ligada à GUI/CLI; sem ele, o nome não resolve.

getent hosts web.localhost
curl -I http://web.localhost:18080/

ss -lunp | grep 5353
journalctl --user -u podstack.service -n 100 --no-pager

# drop-in manual (revise antes)
sudo mkdir -p /etc/systemd/resolved.conf.d
sudo tee /etc/systemd/resolved.conf.d/podstack.conf >/dev/null <<'EOF'
[Resolve]
DNS=127.0.0.1:5353
Domains=~podstack.local
EOF
sudo systemctl reload systemd-resolved

resolvectl query web.podstack.local

Se o Avahi estiver ocupando 0.0.0.0:5353, o daemon tenta conviver com SO_REUSEADDR; se ainda assim o DNS não responder, o journal mostra o aviso. O DNS só sobe com network.bridge=true. Para remover o drop-in, apague o arquivo e recarregue o resolved. Para a maioria dos casos, prefira *.localhost.

Áudio no guest

O áudio usa PipeWire no host e é ativado por máquina. Ligue com podstack machine audio <id|nome> on ou pelo botão Ativar áudio; a machine reinicia se estiver rodando. O guest precisa de stack de áudio compatível (PulseAudio no Debian/Ubuntu; PipeWire no Fedora). VMs antigas podem precisar instalar o stack manualmente.

podstack machine audio dev on
podstack machine info dev
podstack machine logs dev --tail 100

# dentro do guest
aplay -l
pactl info
pw-cli info 0

Se o dispositivo não aparecer no guest, confirme que o áudio está ligado no host, que o guest tem o servidor de áudio rodando e que a machine foi reiniciada após a mudança. O console serial não transmite áudio.

CRIU, checkpoint e cgroup rootless

Sintomas: podstack checkpoint falha com PODSTACK_UNSUPPORTED ou erro do engine; restore não encontra o checkpoint; o container não fica no estado esperado após o restore.

criu --version
criu check
stat -fc %T /sys/fs/cgroup
podstack inspect web | head
podstack ps --all

O checkpoint/restore usa CRIU e depende do host. Em rootless, é preciso cgroup v2 com delegação e o binário criu. Muitos hosts não permitem o checkpoint rootless. Se o host não oferecer suporte, use rootful (opt-in) ou trate o recurso como indisponível. Não use kill/pause como substituto de um checkpoint persistente. O restore espera um checkpoint criado para o mesmo container.

Compose e builds

Se o Compose não sobe, confira o provider e o socket do Podman:

docker-compose version
podstack compose ls
PODSTACK_COMPOSE_PROVIDER=docker-compose podstack compose up ~/projetos/app

O erro PODSTACK_COMPOSE_PROVIDER_MISSING indica que nenhum provider foi encontrado; instale docker-compose ou configure PODSTACK_COMPOSE_PROVIDER com o binário disponível. O compose up do CLI sempre roda destacado e recebe o diretório do projeto, não um -f.

Em um build que falha, confira contexto, Dockerfile, --build-arg e o histórico. Para múltiplas plataformas, o host precisa de binfmt_misc para as arquiteturas estrangeiras.

podstack builds
podstack build ./app -t local/app:dev -f Dockerfile
podstack build ./app -t local/app:multi --platform linux/amd64,linux/arm64

Updates

podstack update --check
podstack update --check --json --channel beta

update --check não instala nada. Exit 3 significa que há versão nova; exit 1 indica que a checagem está indisponível. A atualização é feita pelo gerenciador de pacotes (sudo dnf upgrade podstack/sudo apt upgrade podstack) ou pelo canal que você usa. Erros PODSTACK_UPDATE_SIGNATURE/PODSTACK_UPDATE_MANIFEST indicam feed ou assinatura inválidos; não contorne a verificação. Um feed sem chave retorna unconfigured.

Códigos de erro PODSTACK

Código Significado O que fazer
PODSTACK_DAEMON_UNAVAILABLE O CLI não conseguiu conectar ao podstackd. Confira o socket e o journal.
PODSTACK_ENGINE_UNAVAILABLE Podman/socket indisponível. Ative podman.socket, confira podman info e a versão.
PODSTACK_HELPER_REQUIRED A ação exige o helper privilegiado. Instale/habilite o helper e autentique no polkit.
PODSTACK_HELPER_UNAVAILABLE O helper não respondeu. Confira systemctl status podstack-helper.service e o journal.
PODSTACK_PERMISSION_DENIED Permissão negada no socket, arquivo ou grupo. Verifique UID, modo 0600 e acesso rootful.
PODSTACK_NOT_FOUND Container, machine, arquivo ou recurso não existe. Confira nome/ID com ps --all/machine list.
PODSTACK_CONFLICT Nome, porta ou subnet em uso. Escolha outro nome/porta ou remova o conflito.
PODSTACK_VALIDATION Valor de configuração inválido. Consulte podstack config schema e corrija.
PODSTACK_INVALID_PARAMS Argumentos ou parâmetros inválidos. Revise a sintaxe e as flags.
PODSTACK_UNSUPPORTED Recurso não suportado no ambiente (KVM, CRIU, virtiofsd, Caddy). Instale/habilite o componente ou use a alternativa.
PODSTACK_TIMEOUT A operação excedeu o tempo. Verifique engine/VM/rede e tente novamente.
PODSTACK_CANCELLED O job foi cancelado. Reexecute quando estiver pronto.
PODSTACK_COMPOSE_PROVIDER_MISSING Provider Compose não encontrado. Instale docker-compose ou defina PODSTACK_COMPOSE_PROVIDER.
PODSTACK_UPDATE_SIGNATURE/PODSTACK_UPDATE_MANIFEST Feed inválido ou assinatura rejeitada. Confira rede, URL e chave; não ignore a assinatura.
PODSTACK_IO_ERROR Falha de arquivo, SSH/SCP, arquivo compactado ou rede. Confira caminhos, permissões, espaço e conectividade.
PODSTACK_DB_ERROR Falha no SQLite/estado do daemon. Reinicie o daemon; se persistir, preserve o estado e gere um report.
PODSTACK_CONFIRMATION_REQUIRED Ação destrutiva sem confirmação explícita. Use a GUI ou --force/--yes quando o comando oferecer.
PODSTACK_CONFIG_WRITE_FAILED Não foi possível gravar a configuração. Confira permissões de ~/.config/podstack e espaço.
PODSTACK_BUILD_ERROR O build falhou. Leia a saída do podstack build e confira contexto/Dockerfile.
PODSTACK_EXEC_FAILED O comando no container falhou ao executar. Confira se o container está rodando e se o comando existe.

Logs e diagnóstico avançado

Use o journal do daemon, o podstack doctor e o podstack top para monitoramento. Para o estado do engine, podman info. Para inspecionar um container, podstack inspect. Para um relatório redigido, podstack report --include-logs.

journalctl --user -u podstack.service -n 200 --no-pager
journalctl --user -u podstack.service -f

podstack doctor
podstack top --once --plain
podstack system df --detailed
podstack system disk
podstack report --include-logs

Se o daemon não responder, o CLI retorna exit 7; se um check do doctor falhar, exit 1. Erros de engine PODSTACK_ENGINE_UNAVAILABLE também usam exit 7. O formato de erro do RPC é {code, message, detail, remediation}; a CLI mostra a mensagem, o detalhe e a ação sugerida.

Limitações relacionadas

  • Console serial sem VNC; não há console gráfico para diagnosticar o boot.
  • Export/clone não preservam snapshots internos do qcow2.
  • Portas não publicadas não são suportadas em rootless (T6-10).
  • T5-07/T5-08 parciais: sem NodePort/LoadBalancer e sem troca de contexto automática por projeto.
  • Flatpak é cliente de um daemon/helper instalados no host.
  • CA, DNS *.podstack.local e portas 80/443 ainda não têm fiação automática na GUI/CLI.
